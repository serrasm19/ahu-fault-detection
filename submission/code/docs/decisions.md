# Decisions and assumptions

Back to the [project map](00%20-%20Project%20map.md).

Short log of the choices I made and why. Newest at the bottom.

| # | Topic | Decision | Why | Ask the client |
|---|---|---|---|---|
| 1 | Location and holidays | I assume the buildings are in Singapore and use the Singapore public holiday calendar. | The data is in UTC+8 and the office closed on exactly the 7 weekdays that are Singapore 2025 public holidays. Kuala Lumpur (also UTC+8) has different holidays. | Where are the three buildings, and which holiday calendar do they follow? |
| 2 | Rows I score | I only learn from and score rows with the fan on. With the fan off I predict normal. | The brief scores only fan-on rows. With the fan off there is no air flow, so most faults can't be seen. | Do you also want alerts when the AHU is off, for example a sensor that drifts overnight? |
| 3 | Shifted office week | I move the B1 rows stamped from 1 June 16:00 to 8 June 16:00 8 hours later (`fix_clock_shift()`). In the first 8 hours I move only the second copy of each stamp, and drop the 13 stamps with a single row (their clock is unknown). Test data is not touched. | That week was saved in UTC instead of local time. It explains the night running, the 96 duplicates on 1 June and the 8-hour hole on 8 June. | Did the office BMS change its time settings in early June? |
| 4 | Repeated mall day | I keep one row per machine and stamp on 14 February and fill an empty value in one copy with the other copy (`merge_duplicates()`). | The two copies never disagree on a value; they only differ by a few empty values. Nothing is lost. | How was the mall data exported? Was it joined from several files? |
| 5 | Missing data | I don't fill the hospital 8-day gap (10 to 18 March) or the short 5-10 minute gaps. Features will use time-based windows. | There is no data to fill the long gap from, and invented values would teach the model a fake normal. Short gaps are only 0.3% of the slots. | Was the hospital BMS or its network down from 10 to 18 March 2025? |
| 6 | Empty values | I keep the 0.2% empty values as NaN. | Too few to matter. The model must accept NaN, or I fill them at feature time. | |
| 7 | Fan power in watts | I divide the fan power of B3-AHU-04 by 1,000 from 1 to 21 April (`fix_power_units()`). | The values are exactly 1,000 times too big in those three weeks, with the fan on and off. | Was the meter of B3-AHU-04 changed or reconfigured in April? |
| 8 | CO2 glitches | I set CO2 readings of exactly 0 or 5,000 ppm to NaN (`blank_co2_limits()`). | They are the limits of the sensor range, mixed with normal readings: a glitching sensor. | Was the CO2 sensor of B2-AHU-03 checked in January or February? |
| 9 | Frozen sensors | I set a temperature to NaN when it stays at exactly the same value for 6 hours or more (`blank_frozen()`), in train and test. | Normal sensors never stay flat for more than about 1.5 hours. A frozen value looks normal and would hide or fake a fault. | Why did B1-AHU-07 return air (May) and B2-AHU-08 supply air (July) stop updating? |
| 10 | Supply air | I use the error `sat_c - sat_sp_c`, never `sat_c` alone. | Each machine has a fixed setpoint, but setpoints differ (12.5 to 14.5 °C). | |
| 11 | Start-up | No alarms in the first 30 minutes after the fan starts (`minutes_since_fan_on()`). | Every start looks like a weak radiator for about 30 minutes (supply air up to 5 °C too warm). | |
| 12 | Machines at their limit | Features are relative to each machine's own normal, not fixed thresholds. | B1-AHU-05, B3-AHU-02 and B3-AHU-09 run with the valve at 100% most of the time, labelled normal. A global threshold would alarm on them every day. | Are these three machines known to be undersized? |
| 13 | Drift | I validate in time order, and don't use absolute filter pressure or fan power as fault signals. | Filters get dirty for months and are then replaced, so normal values change over time. | When were the filters replaced? |
| 14 | Missing label | For training I label B1-AHU-11 as a stuck flap (`oa_damper_stuck`) from 22 April 07:00 to 30 April 16:00. | Same fingerprint as the labelled stuck flaps (no outdoor air, flap command 70%, CO2 +700 ppm) and a visible repair on 30 April. Left as normal, it would teach the model that a stuck flap is healthy. | Was there a work order for B1-AHU-11 at the end of April 2025? |
| 15 | Lying thermometer | I detect it with the offset at rest (supply minus mixed air, fan off for an hour) and carry the last value to the next fan-on rows. | With the fan on the controller hides it. At rest the bias shows clearly (about ±2.5 °C vs a normal -0.5 °C). | Can the BMS log a short daily check with the fan off on the 24/7 machines? |
| 16 | Scoring | I score by event on fan-on rows: detected, delay, right type, false alarms per AHU per month (`evaluation.py`). | The brief scores this way. Row accuracy is useless here (always "normal" gives 97.6%). | Can you share the exact scoring rules (how an alarm is matched to an event)? |
| 17 | Validation | Three blocks of about two months, cut on days with no event in progress. Each block is predicted by a model built on the other two. | Only 29 events: training only on the past would leave the first block with almost nothing. No event is split. | |
| 18 | Short alarms | I drop alarms shorter than 2 hours of running. | A real fault lasts days. A few odd rows (a storm, a start) are not worth a site visit. | |
| 19 | Weak radiator signal | I compare the valve with what the same machine needs for the same cooling work (`valve_excess`), not with one fixed value. | A valve is not linear. The fixed value gave 4.7 false alarms per AHU per month, this gives 0.20 with the same detection. | |
| 20 | Framing | LightGBM decides if there is a fault; the physics rules give the fault type inside each alarm. | In validation LightGBM gave the fewest false alarms (0.05 per AHU per month) and the rules the most right types (93%). Together: 100% found, 93% type, 0.05 false alarms. | |
| 21 | Model | LightGBM, small (shallow trees, 200+ rows per leaf), class weights, 10% of healthy rows. | Tabular, threshold-like data with empty values; fast and explainable. Better than logistic regression and random forest in validation. Kept small because there are only 29 events. | |
| 22 | Model features | Only the 9 signals compared with each machine's own normal. | With raw values the right type fell to 76%: the machines always at their limit look like a stuck tap. | |
| 23 | Alarms | Model sure at 80%+, alarms under 2 hours dropped, pieces of one fault up to 6 hours of running apart joined, one type per alarm. | A technician gets alarms, not rows. Without joining, a 17-day fault became 18 alarms. | |
| 24 | New AHU or building | Two weeks to learn its normal, then rules only, then the model once it has its own confirmed work orders. | On a building it never saw, the model missed up to half of the faults; the rules found all of them. | Can technicians close each alarm with "fault confirmed" or "no fault found"? |
| 25 | Alarm threshold | A row is a fault only if the model is at least 80% sure (`ALARM_MIN_PROB`). | Tested 50%, 70%, 80%, 90%: 80% is the highest that still finds every fault, with far fewer false alarms than 50%. | |
| 26 | Model versioning | Each run saves the model and a model card (version, commit, data, settings, validation scores) in `artifacts/lgbm-v<version>/`, tracked in git. No MLflow server for this take-home. | Every prediction file can be traced to its model. A full registry with champion and challenger belongs to production (architecture). | |
